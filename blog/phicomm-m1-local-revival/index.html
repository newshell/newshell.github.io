硬件与网络 · 2026-11-02

斐讯悟空 M1 复活记：让一台失联的空气检测仪重新开口.

从原厂协议本地接管，到免拆 OTA 社区固件迁移：记录一台 M1 的两种复活路线、双 MCU 架构与安全边界。

本文目录先让时间走对它还在等云端抓到真正的 DNS本地接管接入 Home Assistant屏幕亮度控制免拆迁移入口后续固件安全审计写在最后公开资料

家里有台斐讯悟空 M1 空气检测仪，已经闲置了很久。

它倒不是真的坏了。屏幕依旧亮着，温湿度、PM2.5 和甲醛也都能正常测量。只是斐讯早已退场，曾经与它相连的云端服务也随之消失。一台硬件完好的设备，就这样成了一座孤岛。

最近整理家里的智能设备，想着与其让它继续吃灰，不如试试能不能接入 Home Assistant。要求其实不高：先让它连上 Wi-Fi，把时间校准；再想办法接住它上传的数据。没想到，这件小事前前后后折腾了不少时间。

一、先让它知道现在几点

最开始的问题很基础：连不上 Wi-Fi。

M1 使用的是庆科的 EasyLink 配网方案。它不像现在常见的智能设备，可以打开一个热点，让手机连进去慢慢配置。EasyLink 通过无线报文传递网络信息，设备也必须恰好处于接收状态。

开始折腾时，我选错了配网协议，试了多次都没能让设备入网。那时还以为是路由器或者无线兼容性的问题，后来才发现，方向从一开始就走偏了。

真正的症结是配网协议用错了。这次没有借助原厂 App，而是调整为适合 M1 的 EasyLink 配网流程，再配合设备端的按键操作，才终于连上 Wi-Fi。

在 EasyLink 持续发包的过程中，长按 M1 的 Wi-Fi 键约五秒，等图标进入快速闪烁状态，它才真正开始接收配网信息。这次几乎没有等待。设备拿到了 IP，局域网里能 ping 通，重启后也能自动重新连接。

更直观的变化，是屏幕上的时间终于对了。对于一台停服多年的设备来说，能够重新知道现在是几点，已经算是一个不错的开始。

不过事情还没结束。这里的按键时序来自这台设备的实际操作，不代表所有固件版本都完全相同；社区文档还记载了其他配网入口。

二、Wi-Fi 连上了，它却还在等一个不会回应的服务器

时间恢复正常后，M1 右上角的 Wi-Fi 图标仍然闪烁。

起初以为它还没有真正联网。但路由器里能找到设备，局域网通信也没有问题。传感器照常工作，只是数据出不来。

查了一圈才发现，M1 并不是等着别人来读取数据的设备。它习惯主动向 aircat.phicomm.com 发送测量结果，使用 TCP 9000 端口。问题在于，原厂服务已经不在了，设备却依旧按照固件中的逻辑反复尝试联系它。

既然如此，不如在家里的常开服务器上搭一个接收端，让它找到新的落脚处。

最初的办法很直接：在路由器里修改 DNS 解析，把原厂域名指向本地服务器，再启动 TCP 服务，等着 M1 连接。路由器配置生效了；从另一台局域网主机查询域名，返回的也是正确的本地地址。端口已经监听，服务程序也准备好了。

然后就没有然后了。M1 始终没有连接过来。

三、路由器没有错，只是设备根本不听它的

这时候已经折腾了不少配置。继续修改服务器没有多少意义：连 TCP 连接都没有建立，协议解析写得再完整也用不上。

于是换了个思路。与其猜它为什么不连接，不如直接看看它在向哪里发包。

在自己管理的局域网中，对这台设备进行了限定范围、可恢复的短时流量观察，终于看到了它反复发出的 DNS 请求：

M1 → 8.8.8.8:53          aircat.phicomm.com
M1 → 114.114.114.114:53  aircat.phicomm.com

每隔一段时间，它就会重新询问一次。看到这两条请求，之前那些说不通的现象突然都有了解释：路由器的 hosts 确实配置正确，但这台 M1 在此次测试中没有使用路由器 DNS，而是直接向公共 DNS 查询原厂域名。

问题不是服务器没有准备好，而是设备从来没有找到服务器。这也是整个排障过程中最有价值的一次发现。

四、既然找不到原来的云，就在本地接住它

确定了 DNS 请求的实际去向，后面的路就清晰了许多。不需要改变家里其他设备的上网方式，也不必让整个局域网的 DNS 都经过本地服务器。只需要针对这台 M1 和它要访问的原厂域名，在受控环境中返回本地服务地址。

实验里采用了针对单台设备的临时网络路径调整与本地 DNS 应答，并明确保留了恢复原有网络状态的手段。这类手段可能影响设备流量，不能当成适合所有家庭的通用配置；它的作用是确认并解决这一次故障。

接下来，M1 终于开始连接本地服务器。但 TCP 连上，只是另一段工作的开始。

设备启动时还会尝试访问 https://aircat.phicomm.com/device/active；正常运行时，通过 TCP 9000 上报空气数据，并等待服务端按协议确认。报文包含固定头、JSON 内容与结束标记 0xFF#END#，而收发两端对长度字段的处理并不完全相同。

于是继续分析报文结构、数据字段和 ACK 机制，一点点补齐这些交互。原本发往斐讯云端的数据，终于能够在本地被接收、解码。

温度、湿度、PM2.5、甲醛，一个都没少。当然，这并不意味着恢复了原厂云的全部能力；只是这台设备目前需要的激活与测量上报流程，已经有了一条能够工作的本地通路。

五、最后一步，让它进入 Home Assistant

数据能收到之后，接入 Home Assistant 就有了基础。此前创建的四个实体一直显示 unknown。它们虽然出现在界面里，却没有真正的数据来源。

现在，数值终于出现了。

本次留存的真实设备照片中，甲醛显示为 0.03 mg/m³；Home Assistant 截图中对应的甲醛值为 30 µg/m³。两种写法单位不同，却是同一个浓度数量级：0.03 mg/m³ = 30 µg/m³。温度、湿度和 PM2.5 也都显示正常。两张照片并非同一时刻拍摄，因此不拿细微的温湿度差异判断协议精度。

更重要的是，这不是一次偶然的读取。后续观察中，TCP 连接保持着，设备继续上报，Home Assistant 的实体也在刷新。

至于 Wi-Fi 图标是否彻底停止闪烁，倒不必再用它判断一切了：不同测试阶段曾出现过不同的图标状态，不能用一个小图标代替实际的连接和上报证据。

这组实测数据来自真实设备及 Home Assistant 截图。文中的网络原理图是单独绘制的示意图，不是实验现场照片，也没有用 AI 重绘的屏幕来冒充测量记录。

六、让它重新听得懂指令

四项数据都进入 Home Assistant 之后，原以为这件事可以收工了。但 M1 的屏幕还亮着：既然它会主动连到本地，能不能让它也听听我们说话？

这次没有刷机、拆机，也没有安装 Homebridge。设备依旧主动连接自己熟悉的 aircat.phicomm.com:9000。本地的 phicomm_aircat 自定义集成接过原厂服务器的角色：接收温湿度、PM2.5 和甲醛数据，在现有 TCP 连接上回 ACK、发心跳，也负责发送亮度与睡眠计划。它仍然说着原来的语言，只不过电话那头换成了家里的 Home Assistant。

先在字节层听懂它

抓到的帧大致是这样组成的：23 字节设备头 + 00 + 长度字节 + 00 00 + 消息类型 + JSON + FF 23 45 4E 44 23。最后六个字节并非普通字符串，而是 0xFF 加上 #END#。如果一上来就对整个 TCP 数据使用 decode("utf-8", "ignore")，那个非法 UTF-8 的 0xFF 会悄悄消失，随后再找帧尾自然找不到。处理二进制协议，第一步不是急着转字符串，而是先在字节层面拆帧。

包里面的 JSON 倒很直白。温度对应 temperature，湿度是 humidity，甲醛是 hcho，PM2.5 却用了个不太直观的键名 value。数据上报的消息类型为 4；亮度是 2，睡眠计划是 1，心跳/应答涉及类型 5。服务器也不能简单回一句 OK：ACK 要保留设备报文前 23 字节的上下文，再拼上服务端的应答体，否则持续上报可能不稳定。

一条亮度命令，两个坑

找到的亮度命令很短：{"brightness":"50","type":2}。但早期测试中，网络上看得到控制帧，屏幕却没有反应。长度字段一度是重要线索：固定写成 0x37 的做法曾出现在测试过程里，但它既不是所有命令的通用常量，也不能仅凭一次响应断言帧格式已经彻底搞清楚。正式实现按整帧实际字节数生成长度字段；例如 50% 的帧为 62 字节（0x3E），100% 为 63 字节（0x3F）。

关屏终于有效了，100% 亮度也能执行，却又遇到第二个问题：有时很快，有时要等十几秒。原因之一是旧代码把命令挂起，等 M1 下一次上报才附带发送；而设备上报间隔并非永远固定。后来改为在当前活跃的 TCP 连接上立即发送亮度帧，再补发心跳，还要协调 ACK 和控制命令的写入，避免它们抢在一起。

即便如此，“发出去”和“屏幕真的变了”仍是两回事。一次单次测量中，25% 命令的 HA API 耗时约 40.6 ms、TCP 写出约 36.5 ms；100% 则分别约 6.7 ms 和 4.2 ms。这些只代表软件链路的延迟，不是屏幕完成调光的时间，更不能推成长期平均性能。

同一台设备，不该有两个指挥者

设备断线重连、旧连接迟迟不释放时，同一台 M1 可能留下两条 TCP 连接。若每一条都回 ACK、发控制命令，同一操作就会重复发送，界面看起来成功，设备却表现得难以捉摸。后来按设备标识对连接去重，只让最新的活跃连接负责命令，及时清理旧连接及写入锁，并给连续操作留出适当的静默窗口。阶段性日志中才稳定看到 1 device(s), 1 connection(s) available。

不只是亮度，还能把睡眠时间交还给设备

这台 M1 的屏幕实际上只有 0、25、50、100 四档，谈不上连续调光。但它还接受睡眠计划：type=1，字段包括 sleep、startTime 和 endTime。后两个时间以“当天零点起经过的秒数”表示，而不是 HH:MM 字符串。现在 HA 里可以配置睡眠开关、开始时间与结束时间，再把计划写到设备中；计划由 M1 自己执行，而不是靠 HA 到点发一条临时关屏命令。

Home Assistant 提供了一个固定档位的 select，也把屏幕包装成 light 实体。这样通过 HA 原生 HomeKit Bridge，苹果“家庭”里就能把它当成一盏可调光的灯来操作，不需要额外运行 Homebridge。只不过这是一盏“假调光灯”：HomeKit 的连续滑块最终仍会映射到设备支持的离散档位。仪表盘首页放一个好用的亮度控制，全部设备页则保留精确选择档位的入口。

界面显示成功，设备未必真的执行

这一路最值得记住的，倒不是某个十六进制常量，而是一个很容易踩中的误判：HA 显示成功，只能说明命令走到了软件链路，不等于设备真的执行。亮度没有设备状态回读，所以 HA 采用乐观状态，显示的是最近发送的档位。睡眠设置也不应假装有持续回读。

后来验证一项控制，会依次看三层证据：HA 的实体、日志和 Logbook；网络抓包确认命令确实发出；最后直接观察实体屏幕有没有变化。HomeKit 还要额外确认 Bridge 加载正常、实体被实际暴露，以及 Apple 家庭中的操作能够在 HA Logbook 中找到来源。只把实体写进 HomeKit 包含列表，并不能算接入成功。

这套方案终究不是产品级接口。明文 TCP 没有认证和加密，只应放在可信局域网；本地 HTTPS 激活应答占用 443 端口，不应暴露公网；定向 DNS/ARP 接管需要网络权限和停止后的恢复措施，能通过路由器的静态 DNS 解决时，应优先使用更简单的方式。有时旧 TCP 还显示在线，设备却已不再上报，这种“假在线”仍需要结合最近收到的有效数据帧判断，而不能只看连接数或某个传感器的 last_updated。不同固件、容器网络和端口条件也可能需要重新适配。

至于重命名、分享、账号绑定或解绑，那是原厂云上的账户业务，不是这台空气检测仪必须具备的本地能力。我们没必要为了看起来“完整”，把已经消失的云平台再造一遍。

七、另一条路：不拆机，也可以换一套固件

写到这里，我以为 M1 的出路无非两种：继续陪着原厂协议折腾，或者拆开设备刷机。后来看到 PHICOMM COMMUNITY 的《M1 原厂配网与免拆安装》，才发现还有一条挺有意思的路：不拆机，也能通过原厂留下的 OTA 能力迁移到社区固件。

这篇社区教程把事情分成了两步。首先让原厂 M1 连上 Wi-Fi：部分固件可以在机身进入配网模式后，连接 EasyLink_XXXXXX 热点，经设备自己的 HTTP 8000 接口写入无线配置；另一条经过验证的免 App 路径，是使用支持 monitor 模式与帧注入的 Linux 无线网卡发送 EasyLink V2 数据。普通 UDP 发包并不等于 EasyLink V2 帧注入。这也再次提醒我：配网不成功，先确认使用的究竟是不是正确协议。

设备入网之后，社区提供两种迁移方法。一种是利用原厂已有的 /OTA 接口，在局域网直接上传经过校验的完整镜像；另一种更巧妙：在具备 dnsmasq 和 nftables 的路由器上，只针对这台 M1 重定向 DNS，再由局域网服务器模拟原厂激活与更新接口，让设备主动下载社区固件。教程明确要求核对镜像哈希、保持供电、确认设备身份与最终固件版本；“下载完成”或“服务器返回成功”都不等于设备已经刷写并正常启动。

它使用的原厂域名、/device/active、TCP 9000，与这次本地接管时遇到的线索很相似。但相似不代表方案相同：社区教程把这些接口当作迁移的跳板，迁移结束后可以清除临时 DNS 规则；我现在的方案则是保留原厂固件，让 Home Assistant 长期接过它原本连接的服务端，继续收数据、回 ACK，并发送亮度与睡眠命令。

两条路各有代价。不刷机的好处是设备现有功能不必冒刷写风险，代价是要持续维护私有协议、端口与 DNS 接管；免拆 OTA 可以减少对旧云协议的长期依赖，但仍然是真正的刷机，要承担固件兼容、供电中断和恢复的风险。尤其“免拆机”和“不刷机”，绝不是一回事。

对这台已经能接入 Home Assistant、控制亮度与睡眠计划，还能进 HomeKit 的 M1，我暂时更愿意让它继续按照原来的方式工作。社区教程则留下了一个有价值的后备选项，也提示未来可以研究更温和的、按设备限定的路由器 DNS 重定向，少依赖对网关 ARP 的临时调整。前提依然是路由器确实支持相关规则，而不是照抄一组命令就当成通用解法。

八、后续固件：从“给原厂协议续命”到“让设备重新有维护者”

本地接管并不是 M1 唯一的终点。它让设备沿着原来的协议继续工作；社区固件则试图给设备换上一套仍然有人维护的系统。两条路线不是简单的替代关系，而是把维护成本放在了不同的位置。

路线做法收益与代价
原厂固件 + 本地接管在 Home Assistant 一侧模拟原来的云服务，继续使用设备现有 TCP / JSON 协议。不刷机，保留原厂行为，过程相对可逆；但要长期维护私有协议、DNS 与服务端兼容，功能上限由原厂固件决定。
社区固件迁移 Wi-Fi MCU 固件，并按需要单独更新传感器主控；使用社区维护的 WebUI、MQTT、Home Assistant discovery 和本地控制。减少对原厂云和旧协议的依赖，获得公开源码与持续更新；但要承担刷写风险，以及固件、主控、前端和配置之间的版本维护。
本地接管，是让 M1 继续沿着原来的电话线工作；社区固件，则是给它换上一套仍然有人维护的神经系统。

先看清楚：M1 里面有两颗 MCU

社区项目最值得先弄明白的地方，是 M1 并不是一颗芯片包办所有事情。它有两套独立的固件和版本号：

模块芯片主要职责更新方式
Wi-Fi MCU / 联网模块EMW3080（具体硬件资料也标注 EMW3080B / MK3080B）Wi-Fi、网络通信、本地 WebUI、MQTT。通过设备网页更新 Wi-Fi 固件。
传感器主控ATSAMD20G18A与传感器通信，控制屏幕、按键、蜂鸣器等设备侧功能。通过单独的主控升级流程更新，不走普通 Wi-Fi OTA。

所以，网页上显示 Wi-Fi 固件升级成功，不代表传感器主控也升级了。双区域显示、双击动作、PM2.5 平滑等能力，需要联网固件、前端和传感器主控达到对应版本并彼此配套；普通 OTA 不会替你把两颗 MCU 一起更新。版本读取失败时应当按 unknown 处理，而不是根据 Wi-Fi 版本猜测主控版本。

社区文档目前建议原厂传感器主控 11.x 迁移到开源主控；原厂 17.1.2.3 / 17.x 的差异较大，暂不建议迁移。只想恢复原有 PM2.5、甲醛、温湿度读数，并不需要为了“完整升级”而额外刷传感器主控。先读清设备信息，再决定是否有升级必要。

“免拆机”不等于“没有刷写风险”

社区教程提供了利用原厂 OTA 能力进行首次迁移的路径，因此可以不拆外壳、不接串口；但它依然会写入 Flash。“免拆”描述的是物理操作方式，不代表没有风险，也不代表失败后一定能从网页恢复。

M1 首次迁移有明确的文件边界：原厂固件至少需要达到 0.9.21，并按教程使用对应型号的完整原生 OTA 镜像。原厂升级接口不接受社区后续更新使用的签名包装文件。迁移之后，正常社区固件更新使用经过签名的 .ota.bin.signed；.all.bin 是完整 Flash 镜像，属于有线刷写用途，不能当作 OTA 文件上传。文件类型看起来相似，实际用途不能混用。

迁移前先确认设备型号和原厂版本，从官方发布页下载对应镜像并核对同一 Release 的 SHA256SUMS；备份可备份的配置，保证供电稳定，写入期间不要断电或重启。迁移完成后，按教程重新连接设备热点（例如 M1-AP-XXXXXX）或访问 192.168.0.1 配网，再检查实际运行版本和设备功能。若 WebUI 已无法访问，应按对应的有线恢复流程处理，不能把“免拆迁移”理解成永远不需要恢复手段。

原厂 OTA 接口上传镜像与定向 DNS 让设备主动下载，是两种不同的迁移入口；无论选择哪一种，都应把临时 DNS、HTTPS 应答服务和测试路由限制在这台设备上，并在迁移结束后清理。尤其不要把实验用的域名重定向、ARP 规则或临时服务遗留在家庭网络里。

版本快照：稳定版与候选版分开看

截至 2026 年 11 月 2 日，社区下载页将 v0.9.27 标为稳定版，将 v1.0.0-rc.5 标为 Beta 候选版。RC5 于 10 月 31 日发布，仍需手动下载和安装，不会自动替代稳定 OTA 通道。

候选版v1.0.0-rc.52026-10-31Beta 测试；需要核对机型、变体、累计变更和配套组件。

这里还要避免一个常见误读：候选版发布说明会累计展示 RC 系列的变化，不能把所有功能都说成是 RC5 当天新增。RC4 阶段已经引入 HTTP、设备 MQTT 和 UDP 业务默认使用 MessagePack 的通信调整，旧 JSON 业务路径被移除，Home Assistant 侧保留 compact JSON；旧脚本需要适配，并使用匹配版本的前端和平台服务。RC5 则继续修复认证、通信和网页问题，并补齐 M1 远程读数等能力。升级前应看完整累计说明，而不是只看版本号。

候选版的 M1 能力重点包括：两个显示区域分别配置数据源、有效期和显示格式；双击动作；PM2.5 三样本中值与自适应平滑；外部数据映射与过期回退。社区固件的其他扩展还包括外接 SCD40 CO₂、BMP388 / BMP390 气压，以及更完整的颗粒物数据。需要注意，SCD40 是外接传感器，不是 M1 原机凭空增加了 CO₂ 测量能力；部分传感器扩展和提示音、RTTTL 闹钟等功能也早已在此前稳定版本逐步加入，并非全部属于 RC5 新特性。

候选版的设备发现与平台接入也在继续演进：包括 mDNS 发现、带密码配对的 UDP、TMCP v2 MQTT，以及 Home Assistant discovery。配置备份与恢复不只是导出一份 JSON；恢复时还会检查设备型号、变体、配置版本和内容，避免把另一型号或不兼容版本的配置直接写回设备。网页认证也要按实际版本理解：未设置管理密码时可能无需登录；设置后使用对应的会话 / token 机制，并保留部分 Basic Auth 兼容路径。UDP 配对和外部 MQTT broker 的认证仍是独立配置，不能把网页密码当成所有链路的统一凭据。

设备侧功能则包括四档屏幕亮度、睡眠计划、闹钟音、RTTTL 音乐，以及单击、双击和长按等按键动作。这里同样要看主控能力：Wi-Fi 固件提供网页和网络接口，真正驱动屏幕、蜂鸣器和按键的是 ATSAMD20G18A；缺少匹配主控版本时，网页可能隐藏功能或明确提示能力不足。

还要把 HomeKit 的边界说清楚：M1 本身不是原生 HomeKit 设备。本文现有的 Apple 家庭控制，是通过 Home Assistant 的 HomeKit Bridge 暴露实体；社区固件自身的相关桥接仍属实验能力。DAIKIN hub 变体上的可选 HAP 桥接是另一条产品路线，不应套用到 M1，也不能把 HAP 说成 Matter。

Wi-Fi 固件、传感器主控、前端资源和 IoTCloud 平台分别发布，升级其中一项不会自动更新其他组件。升级前应同时核对设备固件、主控、前端和平台的兼容要求。

安全审计：结论必须带上版本边界

除功能外，社区固件还值得从安全边界上看一遍。下面记录的是对一台运行 0.9.27-99770e 构建设备进行的只读检查，只对本次检查对象和检查范围负责，不能自动推定 RC5 也存在相同问题：

  • 未设置网页管理密码时，管理 API 实际处于未认证状态；
  • 部分 HTTP POST 对 Origin 和 Content-Type 的约束不足，测试中观察到恶意来源的 text/plain 请求仍可能进入命令处理层；
  • 设备提供手动 OTA 上传入口，本次检查未观察到明确的 release counter 或最低版本限制；
  • HTTPS OTA 未验证服务器证书 CA，传输层的服务器身份验证不足，固件签名校验因此是关键安全边界；
  • HTTP + Basic Auth 和 MQTT 使用明文传输，不应将管理接口或 MQTT 暴露到不可信网络；
  • 本次检查范围内未发现明显远程后门机制，但这不等于完成了全面安全审计。

也有值得肯定的设计：签名 OTA 使用 P-256 / SHA-256，在写入前验证签名，并在写入后进行 Flash SHA-256 校验和兼容性检查。传输层证书校验不足，与固件包自身的签名验证是两个不同问题；不能因为 HTTPS 没有验证 CA，就忽略 OTA 签名机制，也不能因为固件签名存在，就认为管理 API、明文 MQTT 和本地网页没有风险。

源码对照也需要留出边界。公开仓库保留了 archive/0.9.x 分支，本次参考的源码快照为 2048ff2f6f2a3597f2bc67d89fb56a86e2f24ca5。设备上的精确构建 99770e 没有在公开仓库中找到一一对应的提交。因此文章中的结论应区分三类证据：设备上的实测、相近公开源码能够确认的实现，以及尚未对 RC5 复核的行为。不能用“源码里就是这样”把它们混成一个结论。

两条路线最后怎么选

如果目标是尽量少改动，先让现有设备恢复工作，那么原厂协议本地接管仍然很合适：它保留了设备原来的行为，也已经证明数据上报、亮度和睡眠控制可以在没有原厂云的情况下继续工作。

如果目标是不再依赖已经停服的原厂服务，并且愿意持续跟进社区发布，那么社区固件更适合作为长期路线。它带来的不只是新功能，还有公开代码、版本记录和新的维护者；相应地，维护责任也从私有协议转移到了 Wi-Fi 固件、传感器主控、前端、平台和设备配置的兼容矩阵上。

复活一台设备，不只是让它重新亮起来，而是要为它找到一个还能继续被维护的理由。

九、写在最后

回头看，这次折腾其实解决了三个完全不同的问题：先是 Wi-Fi 配网，让设备重新连上网络，把时间走对；然后是本地接管，让它不再依赖那个早已消失的原厂服务器；最后才是 Home Assistant 集成，让原本只能在设备屏幕上看到的数据，重新流动起来，甚至还能沿着同一条连接控制屏幕亮度。

整个过程中，写服务端、分析协议都花了不少功夫。但真正改变排障方向的，却是那两条不起眼的 DNS 请求。

有时候，解决问题并不需要再加一层配置、再写一段代码。只需要少一点猜测，多看一眼设备究竟在做什么。

硬件没有坏，只是曾经为它提供服务的世界先一步离开了。

现在，至少在家里的这张网络中，它又有了一个可以回应它的地方。
