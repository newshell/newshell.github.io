斐讯悟空 M1 复活记：从 EasyLink 配网到原厂云协议本地接管.

Wi-Fi 连不上、时间不准确、原厂云停服、HA 没有数据——分成三个阶段解决，才不会把问题混在一起。

本文目录第一阶段：Wi-Fi 配网时间校准第二阶段：本地接管DNS 误区与抓包最小范围接管协议闭环第三阶段：接入 HA固件替代路线结论与公开资料

一台斐讯悟空 M1 因原厂服务停运失去了正常的网络使用体验。恢复它，并不是一次性“把云换成本地”就可以：实际过程有三个独立目标。第一步是重新接入 Wi-Fi，验证设备取得地址并把屏幕时间校准；第二步是接管已经失效的原厂域名、激活和上报服务；第三步才是把接收到的测量数据接入 Home Assistant。每一步都要有自己的成功证据。

先让设备联网并把时间校准，再解决它找不到的云服务器，最后让数据在 Home Assistant 里真正可用。

1. 先让设备接入 Wi-Fi：EasyLink 的按键时机

第一次困难其实发生在配网。早期连续尝试发送 EasyLink 配网帧，设备却没有加入网络。怀疑过无线加密兼容性，也怀疑过广播与组播转发，但最终成功的那次操作很简单：在客户端持续发送 EasyLink 帧的窗口内，长按设备 Wi-Fi 键，观察到高频闪烁后完成配网。在本次记录里，长按约五秒后很快取得 DHCP 地址。

这个观察最重要的教训，不是“五秒是所有机器的标准操作”，而是发送配网帧与设备进入接收状态必须在时间上重合。不同版本可能有不同入口。事实上，斐讯社区固件文档还描述了原厂 M1 的 EasyLink_ 热点及按键相关分支，与本次观察并不完全相同，因此不应将某一种按键动作写成不可变的官方规范。

配网成功后设备能在断电重启时重新连接，说明本次网络配置被保存。至于某些固件中的 FTC 配置端口、UDP echo 是否开放以及其他调试入口，都不能仅凭扫描一次的结果推断成所有固件的统一能力。

2. Wi-Fi 连上之后：先解决设备时间

配网阶段的目标很明确：先让这台停服设备重新加入家里的无线网络，并通过网络校准屏幕时间。此前设备无法正常配网；当 EasyLink 发送与设备按键时机正确重合后，它取得 DHCP 地址、局域网可以连通，时间也恢复正确。这是第一阶段的成功，还不代表原厂云服务已恢复，更不意味着 Home Assistant 已获取传感数据。

设备本地温湿度、PM2.5 与甲醛测量依然工作；屏幕上的 Wi-Fi 图标却可能继续闪烁。此时需要分清：无线联网和时间同步已经解决，接下来才轮到原厂域名访问和数据上传链路。

本次设备的无线部分涉及 MXCHIP EMW3080B 系列模块。不同固件的配网入口、FTC 配置端口和状态图标逻辑可能不同，本文所述按键时机来自本次实测，不作为全系列统一规范。

3. 第二阶段：尝试在本地接管失效的原厂云

原厂域名是 aircat.phicomm.com。初步设想是用本地服务器代替已经不可用的云端：在路由器 DNS 中将这一域名解析至常开主机，主机提供 TCP 9000 的数据接收服务，并为启动阶段的 HTTPS 激活请求准备兼容响应。

这个方案的逻辑本身没有问题：对于确实使用路由器 DNS 的客户端，单域名覆盖不会要求把全部互联网流量转发到 NAS。但最早的判断忽略了前提。局域网主机执行 nslookup，返回正确的本地地址，只能证明该主机所查询的 DNS 服务器配置有效，不能证明 M1 采用同一服务器。

结果是服务端口已经监听，设备却始终没有连接。这里需要避免另一种常见误判：端口处于 LISTEN 状态，只证明接收端准备好了，并不证明设备发出了 SYN 或建立了 TCP 会话。

4. 本地接管遇阻：抓包发现硬编码 DNS

为了排除猜测，随后进行了一次限定目标、短时且可恢复的网络观察：仅对本人持有的 M1 进行定向流量捕获，并在实验结束后恢复原始网络状态，而不是修改整个家庭网络的默认路由。

观测结果表明：设备周期性查询 aircat.phicomm.com，但查询目标并非路由器，而是公共 DNS 8.8.8.8 和 114.114.114.114。因此，尽管路由器的 hosts 配置正确，设备仍未从那里取得本地服务地址。这是对先前“路由器 hosts 足够了”假设的直接反证。

请注意，这一结论来自本次固件与抓包记录：说明至少在此次网络状态下，设备绕过了路由器 DNS；并不等于 M1 所有版本都永久硬编码同样的解析服务器。

5. 本地接管完成：单设备 DNS 与假云服务

最终恢复思路并不是继续增加全局 DNS 规则，而是只处理指定设备对原厂域名的请求：在被授权的局域网里，针对单台设备接收并识别这类请求，再向它返回本地服务地址。实际实验采用了面向指定设备的临时网关邻居关系调整与本地 DNS 应答，结束时恢复真实网关信息。

这个方案的边界非常重要：单设备、单域名、限定持续时间、明确恢复路径。它不是普通家庭网络的通用推荐配置。邻居表欺骗或类似透明接管会改变设备的流量路径，存在冲突和中断风险；本文只解释故障原因与方案设计，不提供可以照搬的原始套接字流量拦截程序。

对这类停止服务的 IoT 设备，更可维护的长期方向通常是使用具备显式 DNS 策略的独立网络、受控网关或可更新的开源固件，而不是将临时网络实验当作无风险永久方案。

6. 本地接管的最后一步：激活、上报与 ACK

DNS 的作用只是让设备找得到本地服务。随后还必须满足应用协议的预期。记录中，设备启动期间会尝试访问 https://aircat.phicomm.com/device/active，本地服务提供兼容激活应答；传感数据通过 TCP 9000 主动上报，服务端需要理解报文边界、解析字段并按设备预期返回确认。

本次分析观察到上报数据包含固定格式头部、JSON 内容和 0xFF#END# 形式的结束标记。双方发送方向上的长度字段语义并不完全相同，因此不能仅依据一端消息格式假设另一端格式。ACK 也不是“只要 TCP 收到字节就完成了”，而是需要符合设备应用层行为。

在 Home Assistant 侧，四个测量实体终于从 unknown 变成持续更新的数值。温度、湿度、PM2.5、甲醛的解码由观察到的协议与显示结果互相校验。这里不公布家庭设备身份、实际网络地址、完整原始报文或任何可能被误认为公开协议规范的私有实现代码。

7. 第三阶段：接入 Home Assistant，验证四个实体

完成本地 DNS 与服务端协议闭环后，最后才把数据映射为 Home Assistant 的温度、湿度、PM2.5 和甲醛实体。接入初期四个实体曾显示 unknown，说明 HA 中有实体并不等于设备已经上报；完成接管后，四个实体才出现有效数值，并在后续记录中持续更新。

这一阶段的验收应当分别观察服务端 TCP 会话、有效数据帧与 ACK，以及 HA 实体持续刷新，而不只是打开控制面板看到一次读数。

早期曾记录“本地 TCP 监听后 Wi-Fi 图标停止闪烁”，而后期在正常上报时又观察到白色图标仍可能慢闪。两项观察并不完全一致，因此本文不把图标是否停止闪烁当作 HA 集成的成功标准。

真实设备与 Home Assistant 的现场证据

最终记录保留了两种不同来源的现场画面：M1 实物正面照片显示 PM2.5 为 0 µg/m³、甲醛为 0.03 mg/m³、温度 23.6°C、湿度 66.4%，同时能看到设备右上角的 Wi-Fi 图标；Home Assistant 控制面板截图则显示四个实体，分别为温度 23.5°C、湿度 66.72%、PM2.5 0.0 µg/m³、甲醛 30.0 µg/m³。

需要注意两张截图并非同一时间拍摄，不能把温湿度细微差异解释为协议误差。甲醛数值的单位换算一致：0.03 mg/m³ = 30 µg/m³。这组证据说明数据已可以被 Home Assistant 解码并展示，但持续性仍需依靠连接和重复上报记录证明。保留真实照片原始读数，不使用 AI 重绘的设备画面冒充实验现场。

8. 其他路线：不模拟原厂云是否可行？

路线优点主要限制
维持原厂固件、不接管设备本地测量仍可用云数据上报及联网状态可能异常
路由器 DNS 覆盖 + 本地服务结构简单、改单个域名客户端必须实际使用受控 DNS
隔离网络 / 受控网关 + 本地服务可以显式控制设备流量增加网络维护与兼容性成本
社区开源固件可提供本地控制、MQTT / HA 路线需要核实版本、迁移路径与刷写风险

关于刷机路径，不能再简单地写成“只支持拆机 J-Link”。当前公开的 PHICOMM COMMUNITY 文档列出了 M1 原厂内网 OTA 迁移，以及串口 Bootloader / J-Link 的有线恢复路线，也区分了不同固件版本适用性。另一项 zM1 项目公开了面向 M1 的替代固件资料。它们和本文的原厂固件本地协议接管是不同方案，不应混为一谈。

9. 结语：让数据包结束争论

这次最重要的发现，不是搭出了一个“假云”，而是找到了那个反复指向公共 DNS 的请求。它依次排除了“没有连 Wi-Fi”“服务器没监听”“路由器 DNS 配置错误”等宽泛解释，把问题缩小到设备没有使用受控解析路径。

好的排障不是不断加配置，而是让证据逐步缩小问题范围，直到剩下一个无法回避的事实。

接下来才是把 DNS、HTTPS 激活、TCP 数据上报和 Home Assistant 实体更新连成一个可观测的闭环。对依赖停服云端的旧设备，这种分层思考比某一条命令更有迁移价值。
