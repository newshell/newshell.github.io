树莓派与 PN532：从能运行到可重复.

把模块接通只意味着实验开始。后续更有价值的问题，是如何定位失败和让实验能够稳定复现。

以前的硬件实验记录里，最有成就感的瞬间通常是终端终于打印出设备信息。几年后再看，真正值得留下的却是另外一部分：用了什么连接方式、怎么判断故障是在串口还是射频侧、哪些条件一换就不工作。

这是一篇公开工具文档基础上的设计与排障笔记，不是一次新跑出来的实测报告。以下所有流程仅用于自己有权操作的模块和测试卡；不涉及密钥恢复、UID 改写或复制他人凭证。

先把实验分成三条互不混淆的链

我倾向于把系统画成三段：树莓派 Linux 串口与权限 → PN532 控制协议 → 13.56 MHz 射频目标。看到 No NFC device found 只能说明枚举链路失败，不能立刻判断射频天线坏了。

层级能确认什么不能推断什么
Linux 层设备节点是否存在、用户是否能访问PN532 芯片已正确应答
PN532 驱动层设备握手、协议是否可通一定能识别所有类型的卡
射频层自有测试卡是否被检测能读出卡片受保护的数据

UART 不通时，先检查接口模式与系统占用

PN532 模块可能支持 UART、I²C 或 SPI，具体由板子型号和开关/焊盘配置决定。文档里的 pn532_uart 配置只适用于确实切换到了 UART 模式的设备；不能只因为买到了 PN532 板就照搬串口设置。

Raspberry Pi 3 与其他型号的 UART 分配也可能不同。官方 libnfc 示例既展示了 /dev/ttyAMA0，也针对 Pi 3 的 miniUART 给出了 /dev/ttyS0 的样例。串口控制台 serial-getty、蓝牙复用、enable_uart 以及现代 Raspberry Pi OS 下的 /boot/firmware/config.txt 路径，都应当按当前机型和系统版本核实，不应机械照搬早年的教程。

用于检查的只读操作可以从下列命令开始：

ls -l /dev/serial* /dev/ttyAMA* /dev/ttyS* 2>/dev/null
systemctl status serial-getty@ttyS0.service --no-pager
nfc-scan-device
nfc-list -v

这里列出的命令仅供检查；某些设备节点可能不存在，服务名也可能不同。改变系统串口控制台或设备权限前，应先确认是否还有其他程序依赖该接口。特别注意：不要盲目关闭所有串口服务或修改 boot 配置。

让调试日志可分享，但不给别人看卡片数据

为了定位偶发错误，应该记录每次尝试的时间、软件版本、接口类型、耗时和错误分类。反过来，卡 UID、dump、密钥、认证过程原文以及任何能关联实际门禁系统的标识，都不需要进入常规日志。

下面是一个与任何真实硬件无关、用于展示字段设计的 Python 伪示例；它没有控制读卡器，也不会调用私有实现：

# synthetic event only — no card content is read
from datetime import datetime, timezone

def safe_event(category, elapsed_ms):
    allowed = {"device_missing", "timeout", "no_target", "ok"}
    return {
        "time": datetime.now(timezone.utc).isoformat(),
        "result": category if category in allowed else "unknown",
        "elapsed_ms": max(0, int(elapsed_ms)),
    }

print(safe_event("no_target", 23))

它表达的是一种边界：观察系统运行的状态，不保存被观察对象的私人内容。如果原始错误信息里可能含有设备序列号、用户名、路径等，也要在输出之前脱敏，而不是先写进日志再删。

固定一个变量，才能知道变化来自哪里

实际排障最好从最小矩阵开始，不追求一次测试所有组合。每一轮只改变一个条件，其他内容保持不变：

变量控制方式记录
供电同一测试卡与读卡位置是否枚举、是否发生重置
串口设置同一线缆、同一模块模式设备发现、握手错误类型
读卡距离同一自有测试卡，位置标定检测成功率、超时比例
连续运行固定条件做重复探测失败时间分布、恢复能力
软件版本固定硬件，逐次切换版本是否可稳定复现回归

假设某一组出现失败，首先要确认是不是系统没有找到设备；只有设备握手正常，才把注意力转向 RF 条件。不要在软件不通时就通过更换射频天线或增加发射功率去“试运气”。

从单次命令升级为小服务：异常恢复比启动更重要

如果要把测试台做成长期运行的小服务，最小功能不是 UI，而是健康状态和可恢复性：启动时明确识别设备、轮询采用有界超时、异常时停止或退避重试、退出时释放设备、日志按大小轮转。服务重启不应导致重复上报同一事件，也不要因设备失联进入无上限的紧密重试。

一个轻量架构可以是 systemd → 轮询程序 → 脱敏事件日志 → 本地状态页。不需要把整个读卡记录同步到云端，也没有必要开放远程管理端口。若只是学习 libnfc，从 nfc-scan-device、nfc-list 的只读探测开始已经足够。

衡量完成度时，与其说“服务运行了一周”，不如给出明确的状态转换和失败场景：设备拔出、重新插入、权限不足、启动时串口被占用、没有测试卡、检测超时。这些案例都有非常明确的通过或不通过结果。
